# VALORANT 勝敗通知

許可を得た5人までのRiot IDを登録し、**APIに履歴が返る全モードの試合結果・成績、予約したデスアンレ／デススイフトの判定**をDiscordの指定チャンネルに投稿します。

```text
📢 プレイヤーAは10対13で負け！（コンペ）
🗺️ Ascent｜Jett
🔫 24K / 16D / 5A｜ACS 235｜HS命中率 24.0%
今日（記録分）：2勝3敗
ACT E9A1（記録分）：8勝5敗
現在：3連敗
💬 兄さん、3連敗はアカーン！
```

Cloudflareで1分ごとに確認するため、自分のPCをつけておく必要はありません。第三者のHenrikDev APIを使い、本人のRiotログインやDiscordでの参加操作は不要です。

## 登録

本人から**勝敗をそのDiscordチャンネルに投稿する許可**を得たRiot IDを、[players.json](players.json)に書きます。

```json
[
  { "riotId": "ゲーム内の名前#JP1", "name": "たろう" },
  { "riotId": "AnotherPlayer#1234", "name": "はなこ" }
]
```

`name` はチャットに出す表示名です。省略するとRiot IDの名前部分になります。現在はプレイヤーA・プレイヤーB・プレイヤーC・プレイヤーDの4人を登録しています。登録・変更・削除後は `npm.cmd run deploy` で反映します。削除したIDは次の定期実行で監視対象と保存データから除外されます。

勝利・敗北・引き分けの通知に、[taunts.json](taunts.json)、[comment-tones.json](comment-tones.json)、[meme-quotes.json](meme-quotes.json) から状況に合ったコメントを1つ選んで付けます。異なる文面は合計843種類（既存781種類＋今回の強めの関西弁62種類）。ミームの引用には独自の続きを加えず、その文句だけを表示します。同じ引用を複数場面に割り当てても種類数には重複計上しません。文句を追加・変更する場合はカタログを編集して再配置します。同じ試合・本人・判定条件とカタログが同じなら、再取得・再送で選択は変わりません。カタログ変更後は選択が変わる場合があります。[引用の出典と確認範囲](MEME_SOURCES.md)

## Discord内での戦績照会

`/valo` に13種類のサブコマンドを追加しました。今日・昨日・今週・ACTの成績、直近3試合、ペア相性、直接対決、2人の成績比較、勝率ランキング、最長連勝・連敗、登録者一覧、監視状況、ヘルプを確認できます。保存済みの記録だけを使い、追加のHenrik API問い合わせは行いません。

サーバーメンバーが利用でき、返答は操作した本人だけに表示します。`/death` の管理権限は維持します。新コマンドを使うには `npm.cmd run discord:setup` で再登録してから配置してください。[コマンド一覧と更新手順](DISCORD_SETUP.md)


各secretの入力欄にAPIキー・Webhook URLを入力してください。チャットや公開ファイルには貼らないでください。これでクラウド上の定期実行が始まります。スケジュールの反映には最大15分程度かかる場合があります。

## 相手のPCへのインストールなしで表示する内容

- 試合のマップ・エージェント・K/D/Aを追加表示します。
- コンペでは取得した総スコアを総ラウンド数で割ったACSを表示します。
- HS命中率はヘッド命中数 ÷（ヘッド＋ボディ＋レッグ命中数）です。キルのうち何割がヘッドショットか、という指標ではありません。命中が0件なら表示しません。
- APIに情報がない項目は省略します。エスカレーションにACSは表示しません。
- 試合終了日の日本時間0時を区切り、同じプレイヤー・モードのその試合時点までの勝敗を「今日（記録分）」として表示します。日をまたいで送信された通知には、混同を防ぐため日付を表示します。
- これらは今取得している試合データと保存済みの結果から計算します。新しいAPI問い合わせ・PC側ツールは不要です。ペア相性には下記のDB変更を適用してください。以前の勝敗・ACT用DBが未準備の場合は、通常どおりマイグレーションを適用してください。

### 煽りの切替条件

優先順位は次のとおりです。

1. 同ACT・同モードで5連敗以上：長い連敗向け
2. 同ACT・同モードで3〜4連敗：連敗向け
3. 20キル以上かつキル数がデス数を上回る敗北：奮闘したのに敗北
4. 10デス以上かつK/Dが0.5以下の敗北：個人成績が低調
5. コンペで1〜2ラウンド差の敗北：僅差負け
6. コンペで8ラウンド差以上の敗北：大差負け
7. その他の敗北：通常の煽り

対象外モードや他ACTの連敗を混ぜず、現在の連敗数をコメントに差し込みます。

勝利時は高キル（20以上かつキル>デス）、味方に助けられた勝利（10デス以上かつK/Dが0.5以下）、コンペの僅差勝ち（1〜2R差）、大差勝ち（8R差以上）、通常勝利の順で選びます。3連勝以上・5連勝以上にはそれぞれ専用コメントを優先し、実際の連勝数を入れます。連敗ストップの特別通知も維持します。引き分けでは専用コメントを出し、連勝・連敗をリセットします。エスカレーションの引き分けは従来どおり投稿せず、デスアンレは通常の勝敗コメントと分けた判定通知を維持します。

例：

- 勝利：「勝ったな！ で、次の試合まだ？」
- 敗北：「負け報告は届いたで。勝ち報告の配送予定は？」
- 連勝：「3連勝！ 次の試合まだ？ 主役の続編待ちや！」
- 引き分け：「引き分け！ で、決着編はいつ公開？」

## 特別通知と同じ試合のまとめ

- 同じACT・同じモードで3連敗以上した直後に勝つと、その勝利投稿に「🎊 3連敗ストップ！ 勝利画面、おかえり！！」を追加します。数字は実際の連敗数です。次の勝利では繰り返しません。
- 引き分けは連敗を区切ります。別ACT・別モードの連敗は混ぜません。
- 登録者が同じ試合に参加していた場合、1投稿にまとめ、各人のスコア・成績・ACT集計・連勝連敗・コメントを残します。相手チームに登録者がいても、それぞれの勝敗を表示します。
- APIへの反映に差がある場合、後から取得した人の結果を既存の投稿に追記します。追記はメッセージの編集なので、新着投稿としての通知は出ません。元の投稿が削除されていた場合は、新しい投稿に置き換えます。
- 長い投稿は各人の詳細を埋め込み表示にして、1投稿に収めます。
- この版以降に送る投稿のIDを保存してまとめます。更新前の投稿は編集対象になりません。現在の版にはペア相性用のDB変更があるため、更新時は `npm.cmd run db:remote` の後に `npm.cmd run deploy` を実行します。

投稿の追記はDiscordの[Webhookメッセージ編集](https://docs.discord.com/developers/resources/webhook#edit-webhook-message)を使います。本人のPCへのインストールやRiotログインは不要です。

## 負けても健闘賞・ペア相性

- 敗北時にチーム最多キルなら「🏅 負けても健闘賞」を付けます。同数なら「同率」と明記します。チームの5人全員について有効なキル数が取得でき、最多キルが1以上の場合だけ判定します。勝利・引き分けには付けません。勝敗用の煽りは別に残ります。
- 同じ試合・同じチームの登録者の組み合わせごとに、今ACT・同モードの勝敗数と勝率をまとめた投稿に追加します。3人なら3組、5人なら10組です。敵同士だった試合はペア記録に数えません。
- 引き分けは引き分け数に加え、勝率の分母から除外します。勝敗のついた試合が5試合未満なら「相性はまだ調査中！」と表示します。5試合以上では勝率70%以上・30%以下・その間でコメントを切り替えます。相性の因果関係を判定するものではありません。
- `0003_pair_teams.sql` で同チームかどうかの保存欄を追加します。以前の勝敗だけからチームを推測せず、更新後に双方の所属チームを保存できた試合だけを集計します。APIリクエストは増えません。
- ペア名は長い場合に各24文字までを使います。各人の詳細には通常の表示名を残します。

```text
🏅 負けても健闘賞：チーム最多キル！ ようやった、勝ち星だけ迷子や！

🤝 プレイヤーA＋プレイヤーC｜今ACT・同モード（記録分）：8勝2敗／勝率80%（引分除く）
💬 このコンビ、解散禁止！
```

## スコア・ACT集計・連勝連敗

- スコアは本人のチームを先に「10対13で負け！」と表示します。APIから有効なスコアが得られなければ「スコア未取得」と表示します。エスカレーションで0対0が返った場合もスコアとして表示しません。
- 勝敗数は監視開始後に保存した記録分です。導入前の試合履歴は取り込みません。
- 集計と現在の連勝・連敗は、プレイヤー・ACT・モードごとに分けます。ACTは試合データのACT IDを使い、切替時は新しい集計になります。
- コンペの引き分けもスコア・個人成績・集計を通知します。引き分け数に加算し、「連勝・連敗なし（引き分けでリセット）」と表示します。エスカレーションの引き分けは記録のみです。
- 同時に複数の試合を取得しても、それぞれの試合時点までの成績を表示します。同じ試合を再取得・再送しても成績に重複加算しません。
- ACT情報を取得できない試合は「ACT情報未取得（集計なし）」とし、別ACTを誤ってまとめません。
- 以前の版で保存された通知は、試合のACT・モード・勝敗の構造化データがないため集計に加えません。送信済みの記録は維持し、再投稿を防ぎます。
- API制限や停止による取得漏れがあれば、勝敗数と連勝・連敗にも反映できません。ACT全期間の完全な戦績ではありません。

## 動作と制限

- PC版の取得可能な全モードを対象にします。コンペ・通常アンレ・スイフトプレイ・スパイクラッシュ・デスマッチ・チームデスマッチ・エスカレーション・カスタム等に対応し、新しいキューIDも別モードとして保存します。未完了や本人不在の試合は通知しません。エスカレーションの引き分けは従来どおり記録のみです。
- 初回の過去試合は通知しません。初めてIDを解決できた時刻以降に終了する試合を対象にします。
- 最新5試合を毎分確認します。長時間停止中に5試合より多くプレイした場合や、API側に履歴が出ない場合は取りこぼす可能性があります。
- APIへの結果反映待ちや利用制限により通知は遅れることがあります。制限時は待機し、監視の順番を交代します。
- 同じ試合の重複投稿を防ぎ、送信失敗は次回に再試行します。外部投稿成功直後・記録前の停止では重複する可能性があります。
- Riot IDを変更した場合は設定も変更してください。投稿済みのDiscordメッセージは残ります。
- 本人確認を行う仕組みはありません。運営者が本人の許可を確認して登録する前提です。[HenrikDevの利用条件](https://github.com/Henrik-3/unofficial-valorant-api#before-using-this-api)に従ってください。
- Riot公式APIとは別の第三者APIです。公式APIのProductionキーやRSOの条件を満たす方式ではありません。実API・実Discordとの接続は、実際のキーを設定した後に確認が必要です。

少人数ならCloudflareの無料枠が候補ですが、処理量・CPU時間などの制限があります。[Workersの制限](https://developers.cloudflare.com/workers/platform/limits/)、[D1の料金](https://developers.cloudflare.com/d1/platform/pricing/)を確認してください。

## デスアンレ／デススイフト

予約したアンレまたはスイフト終了後、登録者ごとに次の3条件を判定します。**どれか1つでも該当すればコンペ行き**です。試合に勝ったか負けたかは関係ありません。

1. キル数がデス数より少ない（同数は非該当）。
2. 最終ラウンドで、自分のチーム内の最後のデスだった。敵のその後のデスや前ラウンドのデスは関係ありません。
3. 自チーム5人の中でACSが最下位。丸める前のスコアで比較し、同率最下位も対象です。

```text
☠️ プレイヤーA、コンペ行き確定！（デスアンレ）
❌ KDマイナス：該当（8K / 15D）
✅ 最終R・自チーム内ラストデス：非該当
✅ チーム内ACS最下位：非該当
🚨 次はコンペへ出頭してください。
```

- `/death start player:プレイヤーA` で対象を選び、本人だけに表示されるメニューでデスアンレ／デススイフトを選ぶと予約が確定します。メニューは10分で期限切れとなり、選ぶ前は予約されません。既存コマンドの再登録・Token追加は不要です。`/death stop` で取消、`/death status` で対象モードと期限を確認できます。[使い方](DISCORD_SETUP.md)
- 予約確定より後に開始し、予約から2時間以内に終了する選択モードの次の1試合だけが対象です。ほかのモードや予約前に始まった試合は予約を消費しません。同じモードの待機予約は維持し、別モードを選び直したら切り替えます。対象試合が決まると予約はOFFになります。操作には「管理者」または「サーバー管理」権限が必要です。
- ラストデスはHenrikDev v4のラウンド一覧とキルイベント（`round`、`time_in_round_in_ms`、`victim.puuid`）から判定します。[公式OpenAPI仕様](https://api.henrikdev.xyz/openapi.json)を参照しています。
- ラストデスが同時刻なら、該当する人全員を対象とします。最後のラウンドに自チームのデスがなければ非該当です。
- 本人のデス履歴が総デス数と一致すれば、「最終Rで死んでいない」「本人の最後のデスより後に味方が死んだ」は非該当と判定できます。ほかの味方の過去のデスが欠けているだけでは、この判定を不明にしません。
- ラストデスの該当を確定する場合は、味方全員のデス履歴が必要です。スパイク死や蘇生後のデスが欠けている可能性がある場合は断定せず、データ不足の理由（本人のデス履歴不足、ラウンド履歴未取得など）を表示します。同じラウンド内で本人が複数回死んだ場合は最後の時刻を使います。
- 他に1条件でも該当が分かればコンペ行きと判定します。該当がなく不明な条件が残れば「判定保留」。全3条件が非該当と確認できたときだけ「今回はセーフ」です。
- 予約した試合でラストデスが不明な場合は、初報を送ってから[試合詳細API](https://docs.henrikdev.xyz/api-reference/valorant/get-match-details-v4)を追加取得し、同じDiscord投稿を編集します。追加取得は定期実行1回につき最大1試合、同じ試合は5分以上あけ、API制限中は待機します。通常アンレ／通常スイフト・取消済み予約・確定済みの判定では追加取得しません。
- 後からAPIの情報が補われた場合、最新5試合の監視対象に残っている間は再判定します。確認済みのラストデス判定を保存し、その後の履歴取得で情報が欠けても「データ不足」に戻しません。履歴も詳細APIも不足したままなら、理由付きの判定保留を維持します。
- 同じ試合の登録者は1投稿にまとめ、「デスアンレ判定」「デススイフト判定」と表示します。通常のACT勝敗・連勝連敗・ペア相性の表示とは分けます。
- PC側ソフトは不要です。上記の追加取得・判定保存は既存DBを使い、新しいDB変更はありません。初めて予約機能を導入する場合は `0004_death_sessions.sql` を先に適用します。Discordでの判定通知であり、ゲーム操作は行いません。

## 通知速度と遅延の切り分け

- 送信待ちの結果は、次の監視開始時にAPI確認より先に投稿します。新しく取得した結果も、全員分の履歴取得を待たずに投稿します。
- 取得した1試合のデータに別の登録者が含まれる場合、その人の履歴更新を待たずにまとめます。各人の監視開始日時とデスアンレ予約の有無は個別に確認します。アカウントのPUUIDがまだ解決できていない人は、解決後の取得で追記します。
- API制限の再開時刻がUnix時刻で返る場合は現在時刻との差に直し、待ち秒数と取り違えないようにします。Retry-Afterの小数秒とX-RateLimit-Reset-Afterにも対応します。制限中に問い合わせを連打する処理は追加しません。
- `/valo status` では直近の新規投稿について「試合終了→Bot検知」「検知→Discord送信」を確認できます。後からのメッセージ編集は最初の通知時間を上書きしません。更新前の通知は時間未記録の場合があります。
- ログの `henrik_response` は応答時間・残り回数・キャッシュ関連ヘッダー（取得できた場合のみ）を記録します。`discord_delivered` は終了・検知・送信時刻と各区間の時間を記録します。キーやWebhook URLは含めません。
- 毎分の確認間隔と、Riot/Henrik側への試合結果の反映待ちは残ります。「終了→Bot検知」には確認間隔や取得処理の時間も含まれるため、その時間すべてをAPIの遅延とは断定できません。秒単位の通知を保証するものではありません。

### 雀魂の段位戦速報

`src/mahjong.ts` は雀魂牌譜屋の公開対局一覧を5分間隔で確認します。玉の間の四麻・三麻、東風・半荘が対象です。本人のパスワードや雀魂へのログインは使いません。監視対象の内部ID・表示名・開始日時は `mahjong-bootstrap.encrypted.json` に暗号化し、既存の非公開ブートストラップ鍵で読み取ります。平文の対応表を公開Web配信対象へ置かないでください。

速報は順位・最終持ち点・対局終了時刻と、順位別の3行の関西弁コメントです。放銃、役満、昇降段など対局一覧から確認していない事柄は断定しません。KP報酬は金額とDiscord対応が未設定のため付与しません。VALORANT速報・既存通話報酬とは独立して動作します。

- 開始日時より前に始まった対局は投稿しません。再取得時は対局の固定IDと対象者IDでキューを重複登録しません。遅れて掲載された対局も直近7日間の再走査で拾います。
- 投稿キューをD1に永続化し、並行処理は期限付きの取得権で防ぎます。Webhook成功後・D1更新前の障害は配送が確定できないため、完全な一度だけの配送は保証できません。不明時は15分待って再確認・再試行します。
- 牌譜屋から発行されたAPIキーを Worker Secret `AMAE_KOROMO_TOKEN` に置くと `Authorization: Bearer` で送ります。キーの条件（毎秒1件まで）に合わせ、リクエストの間を1.1秒あけます。`/api/mahjong/status` の `authenticated` で設定の有無だけ確認できます。
- 429は少なくとも1時間待機します。ミラー切り替えや認証チャレンジの回避はしません。対局データの取得に認証が必要な場合は利用可能な取得方法の確認が必要です。
- 牌譜屋自体の反映遅延は数分〜数時間です。サイトの集計内容には誤差がある可能性があります。
- `GET /api/mahjong/status` は人数・対象モード・最終成功時刻・待機理由・配送件数のみを返します。名前・内部ID・Webhook値は返しません。`enabled:true` だけではデータ取得成功を意味しません。`lastSuccessAt` と `error` を確認してください。

取得契約の参照元: [牌譜屋のレコード取得処理](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/source/records/loader.ts)、[順位と同点の扱い](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/types/record.ts)、[モードID](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/types/gameMode.ts)。

初回登録は四麻の玉の間（東風・半荘）。三麻も実装上は扱えますが、対象に含める場合は非公開設定の対象モードを追加します。

### 雀魂の牌譜申請（/paifu）

牌譜屋の取得がAPIキー待ちのため、雀魂のKPは本人の申請と他のメンバーの確認で付与します（`src/mahjong-claims.ts`）。雀魂のデータは取得せず、ログイン情報も扱いません。

- `/paifu url:<牌譜の共有URL> game:<四麻／三麻・半荘／東風> rank:<順位>`。URLは雀魂公式ドメインの `?paipu=` か牌譜IDのみ。形式違い・他サイトは本人だけに返答し、公開メッセージを出しません。
- 申請はチャンネルに公開され、「承認」「却下・取り下げ」のボタンが付きます。承認できるのは申請者以外の登録メンバーだけ。却下は登録メンバーか申請者本人。断られた押下は押した本人にだけ理由を返します。
- 承認時に一度だけ `kp_ledger`（種別 `mahjong`）へ記帳。同じ牌譜を同じ人が二重に申請できず、同じ順位も一人まで。却下・取り下げ後は正しい順位で再申請できます。
- 牌譜の日付が3日以内の対局のみ、1人1日6件まで、承認は72時間以内。
- 金額は `mahjong-kp-policy.json`（**提案値**）：四麻半荘 500/300/200/−300、四麻東風 250/150/100/−150、三麻半荘 500/250/−300、三麻東風 250/125/−150 KP。ラスはマイナスで、残高が足りない分は免除（口座は0未満にならない）。申請表には絶対値を保存し、符号は記帳トリガー `kp_mahjong_apply_v2` が順位から付ける。
- 牌譜屋のAPIキーが得られて自動判定を有効にする場合は、同じ牌譜IDの申請と二重に付与しないようにすること。

### 牌譜の中身の解析（役・放銃・立直・点数推移）

`/paifu` で申請された牌譜と、牌譜屋の速報が見つけた登録プレイヤーの対局（終了から6時間以内、牌譜屋の `uuid`）を、GitHub Actions（`.github/workflows/mahjong-paipu.yml`、10分ごと）が雀魂へログインして読み込み、要約をWorkerへ送ります。WorkerのCPU制限では雀魂のprotobufを解読できないため、取得と要約は Actions 側で行います（`scripts/mahjong-paipu.mjs`、`src/mahjong-summary.ts`）。

- 稼ぎchへの投稿：最終順位と点数、役満・メンバーの放銃・メンバーの満貫以上の和了（局名・打点・役）、各メンバーの和了／放銃（点数）／立直（和了）／副露、事実に合わせた煽り（`mahjong-paipu-voice.json`、煽りレベルに従う）。牌譜にない事柄は書きません。
- 役名は雀魂の設定表（`res/config/lqc.lqbin` の fan シート）から作った `mahjong-fans.json` を使います。役が追加されたら `node scripts/mahjong-fans.mjs` で再生成します。
- 申請との照合：対局の種類と金額は牌譜の値を使います。初回はメンバーの承認が必要で、承認時にその順位の雀魂アカウントを申請者に紐付けます。紐付け後の申請は牌譜だけで自動承認します。別のメンバーに紐付いた席の申請は承認できません。
- 署名：Actions と Worker は `MAHJONG_INGEST_KEY` の HMAC-SHA256（時刻・パス・本文、5分以内）で通信します。キューは申請中の牌譜のみ、1回最大10件、失敗は3回まで再試行します。
- 自動で読んだ対局は、Discordと紐付いた人はメンション、紐付け前の登録プレイヤーは登録名で煽ります（煽りの強さは「普通」）。Discordと紐付いた人には、`/paifu` がなくても牌譜の順位どおりにKPを自動で付与します（自動の申請 `auto:<牌譜>:<user>` として記録するため二重付与されず、1日の申請上限にも数えません）。紐付けは最初の1回の `/paifu` とメンバー承認で行います。読み込み済みの牌譜を後から `/paifu` で申請すると、その場で照合します。
- 申請がなければ雀魂へログインしません（依存のインストールも省略）。公開リポジトリのため、ログには件数とエラーコードだけを出します。

設定（リポジトリの Settings → Secrets and variables → Actions）：

1. `MAHJONG_INGEST_KEY`：32文字以上のランダムな文字列。設定後に「VALORANT Bot check and deploy」を手動実行すると、同じ値がWorkerのSecretに入ります（デプロイのたびにリポジトリの値で更新します）。
2. `YOSTAR_UID` / `YOSTAR_TOKEN` / `YOSTAR_DEVICE_ID`：PCのブラウザで `https://game.mahjongsoul.com` にログインする際の開発者ツール（F12 → Network、`yostarplat` で絞り込み）から取得します。`/user/login` か `/user/quick-login` の応答の `Data.UserInfo.ID`（`UID2` ではない）と `Data.UserInfo.Token`、要求ヘッダー `Authorization` 内の `DeviceID` です。
3. 牌譜屋のAPIキー：`AMAE_KOROMO_TOKEN` に「Bearer 」を除いたトークンだけを登録し、同じくデプロイを実行します。
4. Actions の「Mahjong paipu fetch」を「ログインできるかだけ確認する」にチェックして手動実行し、`login: ok` を確認します。

注意：この値はアカウントへのログイン情報そのものです。チャット・Issue・PRに貼らないでください。非公式の取得方法のため、雀魂の規約上アカウントに不利益が出る可能性があります。牌譜はどのアカウントでも読めるため、サブアカウントの利用を推奨します。ログインに失敗し始めたら値を取り直してください。

### Mリーグ予想（/mleague・/mbet）

公式戦の各半荘で「トップになる選手」「ラスになる選手」をKPで当てる（`js/mleague.js`、`src/mleague.ts`）。

- 倍率：(1着またはラスの回数＋5)÷(試合数＋20) を確率とし、競馬と同じく 1÷確率（胴元なし）。今季の公式結果も加算する。購入時の倍率で確定。
