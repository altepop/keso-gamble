# P12 決闘プログラム専用D1バックアップと復元検証

## バックアップの範囲
- 実際のCloudflare D1本番DBから、`sqlite_master`を読み、`kp_board_duels`、`kp_board_duel_*`、`kp_duel_*`に該当する**全テーブル**を見つけ、全レコード・テーブルDDL・索引・トリガーをエクスポートする。重要な6テーブルが1つでも欠けた場合は失敗扱い。
- PvP申込・着手・精算状態、PvEセッションとその非公開データ、熟練度、検証済み対局受領、戦利品設定・抽選・所持、日替わり記録、シーズンアーカイブ等を**各専有テーブルの実装に応じて含める**。全行の保存であり直近20件・50件・500件の一覧上限はかけない。
- 決闘以外の共有`kp_wallets`、`kp_ledger`、株式・競馬・COACHなどは**この独立バックアップには含めない**。したがって「決闘専有データの完全バックアップ」であり「KESO PLAY全体のDB完全バックアップ」ではない。決闘データを本番に戻す場合は必ず既存KP台帳と突合すること。

## 安全な実行経路
1. マージ後に **同一main SHAのWorker本番配備とスモークがSuccessで完了したときだけ**、`P12 duel D1 encrypted backup and isolated restore` Actions が#768のマージコミットを条件に1回起動する。手動再実行も可能。毎時・毎日などの定期実行や本番Workerのスケジュール変更はしない。
2. 既存のCloudflare Secretを使い、本番D1への**読取り専用**の`sqlite_master`照会と`wrangler d1 export --remote --table...`を行う。D1上でINSERT/UPDATE/DELETEや復元命令を実行しない。
3. Runnerの私的な一時領域でSQLを実際に新規SQLiteへ適用する。さらに暗号文から復号したSQLをWranglerの **ローカルCloudflare D1（Miniflare）** にも実際に取り込み、Cloudflare側のSQL互換性を確認する。全対象テーブル・索引・トリガーの存在確認、全テーブル行数、`PRAGMA integrity_check`を検証する。**サーバー権威の決闘操作やKP精算を再実行しない**。
4. SQLはAES-256-GCM＋scrypt（ランダムsaltとnonce）で暗号化し、暗号文を再度復号して別SQLiteへ復元する。成功時だけ、暗号文JSONをGitHub Actions成果物として**30日間**保存。平文SQL、秘密の対局情報、APIトークンはログや成果物に出さない。
5. 処理中にexport・復元・整合性のいずれかが失敗したらJobを失敗にし、成果物を保存しない。これは**本番バックアップ成功の証拠ではない**ため、PR全体の完了判定も保留とする。

## 復旧時の手順
1. 当該Actions実行の成果物 `keso-duel-d1-restorable-<run-id>` を安全な端末・保管先へ入手する。30日を過ぎればGitHub上では失効するため、**恒久保存が必要なら別の暗号化保管先が必要**。
2. 保存時の鍵を使う。専用 `KESO_DUEL_BACKUP_KEY` Secretを設定済みならその当時の値を利用。未設定の場合は**バックアップ作成当時の`CLOUDFLARE_API_TOKEN`の元の値**が必要。トークンをローテーションすると新しいトークンからは復号できない。作成時の鍵ソースはメタデータにも表示する。
3. Node.js 24以降で `node scripts/duel-d1-backup.mjs verify /path/to/keso-duel-restorable.enc.json` を実行する。これは安全な**隔離SQLite上で実際にSQLを再適用**する検査である。バックアップ生成時にはWranglerによる**隔離ローカルD1の実インポート**も確認する。Cloudflare本番D1は変更しない。
4. 本番へ復旧を実施する場合は別の作業として、復旧先の共有KP台帳・未精算エスクロー・D1スキーマとの整合を検証した**人手承認付きのリストア計画**を策定する。本分割では本番への復元、KPの再精算、資産追加、復旧訓練の実行は行わない。

## 制限・注意
- D1のエクスポートはCloudflare側が処理している間、DBリクエストに一時的な影響が出る可能性がある。運用影響が実際にゼロだったと証明するものではない。
- 初回実データのバックアップが成功したかは**対象Actionsの実行結果で必ず確認**する。コードのテストだけでは完了にしない。
- 共有KP台帳の整合、完全な本番サービスの復旧手順、暗号鍵の独立保管、90日以上の保持、24時間監視・通知・運用監査は別分割の課題として残す。
- #764のシーズンアーカイブはリストア用データではない。#764の初回月曜Cron・D1実保存は引き続き未確認。P10実音・P8実機も人手検証待ち。
