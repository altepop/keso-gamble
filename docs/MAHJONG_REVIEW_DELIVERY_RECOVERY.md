# 牌譜保存と投稿キューの障害復旧

`fix/mahjong-summary-outbox` の修正内容。CI・マージ・配置・実対局の最新結果は、このブランチのPR本文を参照する。

## 再現した問題

従来は `applySummary` が最初に `kp_mahjong_paipu.summary` を保存し、その後で支給と投稿キューへの登録を行っていた。投稿登録に失敗しても、取得キューはsummaryがある対局を除外するため、通知が欠けたままになる。

SQLiteの実テーブルに投稿INSERTを失敗させるトリガーを入れ、修正前のコードで「支給済み、summary保存済み、投稿0件、取得キュー対象外」になることを再現した。これは人工データの障害試験で、本番に障害を注入したものではない。

## 修正

1. 署名検証済みの牌譜をメモリ内で検証し、既存の申請承認・自動支給を行う。保存前の照合では受信済みsummaryを使用し、保存のためだけに先行INSERTしない。
2. 投稿の全パートとsummaryを、既存のD1 `batch` で同じトランザクションにする。summaryは最後に保存する。投稿登録または最後の保存の失敗では全体がロールバックし、取得キューの未完了判定が残る。
3. 再試行では既存の承認・台帳IDで支給を重複させず、既に確定した支給額と遺物補正を表示する。遺物の再抽選や現在の装備での再計算はしない。
4. 並行処理で別の実行が先に完了していたら、新しい投稿パートを追加しない。通常の投稿IDと `allowed_mentions` を維持する。
5. 保存失敗は固定コード `summary_apply_failed` と既存の試行回数へ記録し、受信結果にfailed件数を返す。取得側も保存失敗を実行失敗として扱う。他の対局は処理を続け、同じリクエスト内の同一IDは一度だけ扱う。

## 保持する動作と制限

- 取得の対象期間・上限10件・最大3回の試行は変更しない。恒久障害で3回失敗したものは自動で回し続けない。
- 完了済みの過去summaryを再度キューへ入れない。過去への再投稿・再支給や本番データのリセットは行わない。
- 新テーブル・migration・cron・監視ジョブを追加しない。通常の書き込みはsummary1行と投稿N行で、投稿側の完了確認は主キーで照合する。手動申請は受信済みsummaryの再利用で読み取りを減らす。
- 支給と最後のsummary/投稿batchは、全体で一つのトランザクションではない。先に確定した支給は巻き戻さず、既存台帳から表示を復元する。台帳にない補正を推測で追支給しない。
- 再試行には牌譜の再取得が必要なままで、外部APIが取得できなければ成功しない。Webhookが受理した後の応答喪失による重複送信まで、完全なexactly-onceを保証する変更ではない。
- 認証付き残高APIの本番smokeや、自然な新規三麻/四麻v2の実送達は、従来どおり別の確認事項。

## 検証

人工牌譜と実SQLiteを用い、投稿登録失敗、最後のsummary保存失敗、長文全パートのロールバック、同時受信、複数対局の部分失敗、最大試行回数、通知先なし、完了済み過去対局の除外を確認する。

支給については手動申請・自動支給、ラスの減点・遺物損失・不足分の記録、装備変更後の既存ボーナス表示を比較し、再試行で残高・台帳・不足分の記録が変わらないことを確認する。人工三麻の実ルール由来findingと四麻v2のコメントが、再試行後も保存・キューへ残ることを確認する。
