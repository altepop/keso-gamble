# KESO PLAY / LOOP データ保持・削除ポリシー

決定日: 2026-11-05。最初は **分類と監査を実施し、正本を即削除しない**。金銭に準ずるKP・競馬賞金・馬の記録を消すと、二重支払い・不整合・説明不能を招く。

| 保存対象 | 目標保持期間 | 具体例と扱い |
|---|---|---|
| **永久保存（削除禁止）** | 無期限 | `kp_wallets`, `kp_ledger`, `kp_operations`（購入の冪等性）, `kp_loop_events`, `kp_events`, `kp_horses`, `kp_horse_results`, `kp_state`, `kp_bet_index`, `ml_results` など。歴史・残高・精算・再送防止に必要。|
| **支払・通知の証跡** | 無期限（要圧縮設計） | `kp_delivery` の達成・別途支給記録、`kp_posts` の送信済み重複防止ID。全文本文を一定期間後に縮減できるかは別途検討。IDを安易に消さない。 |
| **ログイン・一時認可** | 期限切れ後7日以内 | `kp_sessions`, `kp_codes`, `loop_oauth`, `loop_sessions` 等。本人認証の失効情報は守る。削除は有効期限とインデックスを確認してから。 |
| **短期APIレート制限** | 2〜7日 | `kp_operation_limits`。すでに一部ユーザー単位で古い分を消している。全件整理は別途整合性確認後。 |
| **詳細監視ログ・一時通知本文** | 30〜90日 | 送信済みのデバッグ情報・配達成功ログ・一時リクエスト本文等。ただし再送キー・監査に使う行は保持。 |
| **ユーザー向け履歴表示** | 直近30〜90日の表示が基本 | UIで古い履歴を省略しても、裏の金融/ゲーム台帳は消さない。期間を選べる表示を検討。 |

## 実装時の安全条件
1. **旧行を削除する前に** どのAPI/トリガー/cronが参照しているかを検索・テストする。購入の冪等性キーやLOOP達成の一意キーは永久保存。
2. 日次の削除対象は **期限つき一時データのみ** に限定。インデックスの `expires` / `at` で対象を範囲検索し、`LIMIT` 100〜300行程度ずつ実施。全テーブルフルスキャン禁止。
3. 既存のcronがあるならそれに載せる。新しい分単位cronは作らない。D1のRows readと書き込み量を先に見積もる。D1の無料枠上限に近い日はクリーンアップを後回しにし、精算を最優先。
4. まず削除せず **対象件数のみ** 数えるdry-run、次にステージング／少量削除、最後に本番。障害時のバックアップと復元手順を確認する。
5. 設定変更やアカウント削除等が別法令・プライバシーポリシーにより要求される場合は、上記の「永久」は上限ではなく整合性保全の初期方針として扱い、適用法令とデータ主体の請求を優先する。
6. 月次でテーブル別 `Rows read`, 行数、DBサイズ、精算未完了件数を記録する。目標は通常日の合計Rows read 200万行未満。これを理由に支払証拠を削除しない。

## 実行の保留
この文書は**保持日数の決定**であり、既存D1を破壊する削除ジョブの開始を意味しない。まず実際のテーブル構造・依存関係・既存バックアップ・件数を確認し、安全な一時テーブルに限って削除処理を別PRで有効化すること。
