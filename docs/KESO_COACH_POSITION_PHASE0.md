# KESO COACH フェーズ0：位置データ

## 分割

1. 実レスポンスの品質観測だけを先に投入します。通常の完了済みコンペ・v4応答から、1 HTTP応答につき最初に選ばれた完了済みコンペ1試合の全キルを調べます。キルを都合よく抽出せず、その試合の欠損も集計します。
2. 本番の観測結果を確認してから、座標を分析の通常読み込みと分離して保存するPRを作ります。未確認の配列の存在だけで保存対応を完了扱いにしません。
3. 過去試合は既存の本人承認・対象範囲・取得制限を尊重し、Henrikから再取得できる試合だけを対象にします。分析ロジック・コーチ画面への組み込みは後のフェーズです。

## 最初のPRで変わること

- 通常のHenrik v4 HTTP応答に、固定パスの件数観測を加えます。追加のHenrikリクエスト、D1クエリ、座標保存はありません。
- 座標は負値と0を含む有限数として検査します。向きは小数を含む有限数で検査し、0〜2πの外にある件数も別に出します。座標のメートル換算や、向きの正規化を行う処理ではありません。
- `kills[].location`、`player_locations` の不存在/null/型不正/空配列を区別します。人物参照は公開仕様のflat `puuid` と既存クライアントにあるnested `player.puuid` のどちらを実観測したかを件数で区別し、衝突・未知ID・重複も数えます。
- キルごとの有効なロスター座標人数/座標と向きの両方がある人数を0〜10人のヒストグラムへ集計します。「10人分がない」ことと「配列にある項目が壊れている」ことを区別します。キルログから生存者を推定して欠損を消すことはしません。
- 配列に被害者がいる件数と、同人の座標がkill.locationと一致する件数も観測します。照合できない場合は、そのフィールドの意味を実測で証明したことにはしません。
- キルは最大600件、各キルの位置配列は最大20件まで調べます。超過は不正/上限超過として区別し、黙って完全データ扱いにしません。
- 公開ログに出るのは固定契約・endpoint区分・件数・人数ヒストグラムのみです。座標値、向きの値、PUUID、名前、試合ID、APIキー、任意フィールドは出しません。既存の保存形式と完了判定も変えません。

## 本番観測

マージコミットに `[coach-position-audit]` がある場合、既存の配備ワークフローが通常のCron応答を短時間だけtailします。各55秒・最大6回で終了し、tailを必ず削除します。別の試合取得、コマンド送信、D1変更は行いません。出力は `COACH_PHASE0_POSITION_EVIDENCE` の許可リストへ再検査します。

無応答は `no-normal-response-observed` とし、0件の座標が返された証拠とは混同しません。取得できた場合も1試合の標本であり、全試合・全モード・全プランを検証したとは報告しません。履歴応答と詳細応答はログに区分を残し、未観測の側を実証済みにしません。

## 保存PRへ進む前の判断

実測で位置/向きが欠ける場合は、何が欠けたかをそのまま報告します。常に10人分あるという仮定を置きません。保存対象の欠損方針などで設計判断が必要になった場合は、選択肢と推奨案を添えて確認を待ちます。

## 承認済みの保存仕様（2026-11-20）

実測はhistory 1試合110キルです。`kill.location`は110/110、
`player_locations`は626人分で全て座標・向きが有効でした。
各キル1〜9人分で、被害者は配列に0/110回でした。
全10人が存在することは保存の条件にしません。detailで同じ品質と断定しません。

- `valorant_match_positions`に1試合1行、`positions_json`（schema 1）を保存します。
- rosterにIDとチームを1回保存し、各frameからインデックスで参照します。
- 各frameにラウンド、時刻、加害者・被害者、被害者座標、返却配列の状態、
  返却数、採用人数、座標数、向きの数、分母10、各カバー率（0〜1）を保存します。
- 欠損・null・不正値を区別し、補間しません。空配列も観測済みの空配列として残します。
- victimLocationの出所は`kill.location`です。`player_locations`に被害者が
  含まれないという実測上の仕様をメタデータに記録し、各frameの実際の包含有無も保存します。
  欠損を死亡・遮蔽と解釈しません。座標単位はprovider-nativeで、メートル換算しません。
- 不明・矛盾するID、重複IDは採用せずrejectedCountに残します。
- 600キル、配列20件、JSON512KiBの上限を設けます。上限超過は切り詰めて保存しません。
- 更新は同一イベント列・全既知値を保持する改善したレスポンスのみ、CASで置換します。
  異なるレスポンスを継ぎ合わせた座標を作りません。
- 通常の分析SELECT・APIレスポンス・UIには位置情報を追加しません。
- 既存の通常取得・承認済みアーカイブ取得のレスポンスを再利用し、保存PRで追加API呼び出しはありません。
  最大128件のハッシュキャッシュで同一レスポンスのD1確認を抑制します。
- デプロイ時は専用ensureスクリプトでテーブルだけを追加します。旧マイグレーションは再実行しません。
- 本番確認は最新1試合の人数・カバー率とD1実読取件数のみを出力し、ID・座標はログに出しません。

過去分の再取得は後続の専用PRに分離します。通常の試合収集やKPの再精算は行いません。

## 座標バックフィル

既存の本人承認スイッチ`coach_all_members:enabled`に従い、収集済みリンク・
ソースPUUIDが一致する競技試合（既存アーカイブcomplete、または従来の3試行を終えたpartial）を再取得します。
`coach_position_backfill`は試合単位の試行台帳で、通常の収集完了状態を変更しません。

- 既存アーカイブの5分枠でdetailを要求しなかったときだけ1件処理します。
  既存処理が優先で、従来のdetail取得予算を増やしません。
- `api_after`を確認し、最大3試行、15分間隔です。先に期限付きの原子的claimを取り、
  同時Cronの重複要求を防ぎます。プロセス停止も無限再試行しません。
- 404はnot-found、取得できても使用可能な位置データがなければ
  no-usable-position-responseとして停止します。一般エラー・内容不一致は3回までです。
- 再取得はHenrik v4 detailだけです。Riot公式APIや推測生成は使いません。
- 過去のKP・通知・精算は再実行しません。位置保存だけです。
- 初回デプロイの読取専用監査は最長330秒、既存Cronの進捗を待ち、
  件数・取得不能理由・カバー率・D1 rows_readだけを出します。
- 1件の保存確認はバックフィル全件完了を意味しません。残件と取得不能件数を分けて報告します。


### 後続デプロイに置き換わった場合の監査

GitHubの本番concurrencyは待機中のrunを新しいmainのrunで置き換えることがあります。
初回マージの文面だけで監査全体を条件分岐すると、実保存の確認が抜けるため、
全デプロイで読取専用の進捗スナップショットを1回採ります。
最長330秒の待機は`[coach-position-backfill]`の印がある配備だけです。
監査はAPI取得・D1書き込み・KP支給を行わず、後続変更を古いWorkerで上書きするための再配備もしません。
