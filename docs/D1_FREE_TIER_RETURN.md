# D1無料枠への復帰計画（Workers Paidは1か月限りの方針）

作成日：2026-11-08。目的はゲーム機能と金融整合性を損なわず、課金期間終了後のFree運用を可能にすることである。

## 契約と復帰基準
- ユーザーからWorkers Paidの解約手続き完了との申告あり。正確な契約終了日と請求状況はCloudflare Billing > Subscriptionsで確認する。コードでは判定できない。
- D1 Freeの読み取り上限500万Rows read/UTC日、書き込み上限10万Rows written/UTC日はアカウント全体で共有。リセットは日本時間09:00。Workersリクエスト数・CPU等の上限も別途確認。
- 課金中にクエリが成功するだけでは無料枠で継続可能とは判断しない。複数日、ピーク利用、深夜cronも含む実測が必要。

## PRと新機能の必須品質ゲート
1. インデックス追加だけでは不十分。SQLごとにEXPLAIN QUERY PLANを実施し、全履歴のSCANや同じ計算の毎分再実行を防止する。
2. 毎分cronの常時全表読み込み、新たな高頻度ポーリング、SELECT *による多行取得、n+1クエリは原則禁止。必要な履歴はインデックスとLIMIT・カーソルを使用する。
3. Steamは既処理IDを記憶するが、監視停止中の未支給実績を処理済みにしてはならない。リンク/監視開始日時、Steam APIでの実績検証、日次5000KP上限、二重支給防止を維持する。
4. VALORANTは監視が直近5試合取得であるため、長時間のD1障害中の全試合救済は保証できない。外部の検証可能な試合IDを用いる追加の照合は別タスクとし、自己申告だけでKPを支給しない。
5. Discord通知では送信されていない参加者を送信済みにしてはならない。重複送信、キャンセル、保留、後からの請求の再現テストが必須。
6. 競馬、株式、カジノ、借KP、遺物とランキングのKP台帳・取引履歴を削除したり推測で補填したりしない。
7. 修正前後に1h/24h SQL Insightsとアカウント全体の日次Rows read/writtenの両方を比較。CI成功、Worker本番デプロイ確認の後、実測で改善判断を行う。
8. D1が無料枠上限に達して拒否された期間のプレイは、Steam等の外部履歴があっても自動反映とは限らない。未支給と既支給を照合し、重複排除を条件に補填を設計する。

## 当面の目標と監視
- 通常日の読み取り量：100万～150万Rows read/日以下が目標（**達成は未確認**）。
- 200万/日超が続く場合は高負荷SQLの再分析。350万の既存警告と400万の既存節約モードは最後の安全網であり、ハードキャップを保証しない。
- Cloudflare D1メトリクスはKESO PLAY/LOOPの両DBを合算する。Insightsのtop-50とGraphQL推定値はそれぞれの集計限界を明記。
- Freeへの移行前は最低数日、可能なら7日間の実測を取る。低利用日だけの結果で安全と結論付けない。
