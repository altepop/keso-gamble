# P9.5 報酬の有効化前検証

## 経済と周回

報酬は本人の種目別コレクションに付く。6種目につきPvE遺物とPvP記念章が各1種類あり、同じ報酬の再抽選で所持数は増えない。換金・譲渡・KP発行は行わない。PvEの攻め／守りビルドはヒントの内容を変え、PvPの確定ルールと精算は従来どおり。

`node scripts/duel-reward-simulation.mjs` の合成例では、同じ相手との24戦は、相手別上限2・4で抽選対象が2・4件。12人を入れ替える24戦は、本人の日次上限8・12で8・12件。通常の3相手・6戦では両候補とも6件。日次上限は相手の入れ替えにも効く。

1種目の初回獲得だけを見ると、毎回同じ確率の独立した抽選で累計獲得確率は `1 - (1 - p)^n`。比較に使った10%では50%に7回・90%に22回、5%では14回・45回の対象抽選が必要。同一種目の試行数であり、試合時間、実際の勝率、上限適用後の日数は含めない。現時点で実プレイ分布に基づく獲得ペースは未確定。確率・上限の候補は比較用で、ポリシー行は本番に投入していない。

## 2026-11-20 ユーザー決定：Phase 9 リリース前ゲートの変更

本節は上記「隔離クラウドD1の調査」に残る旧ゲートの記述に優先する。ロードマップAのPhase 9全体の機能範囲を縮小するものではなく、**分離クラウドD1長時間負荷計測だけ**を完了条件から除外する。

1. **リリース前検証**：PR #630 のオフライン比較を採用する。確率・相手別／日次上限は比較用の仮定であり、本番設定への承認・投入を意味しない。ローカルD1の測定値をクラウド性能や実運用時の余裕の保証とはみなさない。
2. **リリース後監視**：本番D1の読み書き行数・エラー・遅延とCloudflareの利用状況を、リリース後Cloudflareダッシュボードで監視する。日次ピーク、他機能の消費、UTC/JST日境界を考慮し、利用量の危険兆候があれば報酬設定停止・再評価の判断を行う。監視が行われていない状態を「監視済み」と記載しない。
3. **行わない事項**：Cloudflareトークンの提供は要求しない。試験用D1の作成・隔離クラウド負荷計測は行わない。本番D1への検証用書き込みや無断の報酬ポリシー有効化もしない。
4. **Phase 9完了判定**：本決定によってD1計測のブロッカーは解消。ただしPvE攻め／守りビルド機能、サーバー権威の攻略・保存・報酬、既存ゲームの回帰・CI・Pages/Worker配備を実装・検証した事実を別途確認する。未実装機能を「完了」としない。実機Discord 2名遅延、Durable Objects実使用量、認証済みウォレットのスモーク、Discord入口切替の運用は人手ゲートの留保とし、完了条件にしない。


## 2026-11-20 ユーザー正式決定：上限撤廃・#543式PvP（本番未有効）

本節は以前の提案A（PvE日次10、PvP日次8・相手別2）に優先する。ユーザーによる上限設計の正式決定であり、**報酬の本番有効化指示ではない**。

- **PvE**：日次総上限なし、ペア上限なし。勝利10%・敗北0%・引き分け0%。
- **PvP**：同一相手につきJST暦日4試合まで報酬対象。5試合目以降も対戦は可能だがその相手への追加報酬なし。異なる相手との1日の総試合数上限なし。勝利10%・敗北5%・引き分け5%。
- **13戦目以降**：#543の「通算13戦目以降の減衰」は、現在の報酬システムではJSTの日付をまたいだ**本人のPvP報酬対象抽選の通算13回目から**ドロップ率を半分に読み替える案として実装した（勝利5%、敗北／引き分け2.5%）。同一相手の5戦目以降の非対象試合は抽選カウントに入らない。通算はギルド・本人のPvPモード単位で既存抽選台帳全期間を数え、日付でリセットしない。
- #543にあった**確定欠片**は#632の「種目別記念章／遺物」発行基盤に存在しないため、新たな欠片・KP発行機能や「最低1欠片」は実装しない。既存のコレクションの収集結果は維持する。
- 既存の `kp_duel_reward_policy` は日次上限必須のスキーマであるため、後方互換のために存置し、上限NULLを表現可能な `kp_duel_reward_policy_v2` を追加。発行トリガーと表示はv2を参照する。旧ポリシーからの移行・本番設定投入は自動では行わない。
- **有効化未実施**：`guild`（正確なDiscordギルドID）および `starts_at`（UTC epoch milliseconds、開始日時）の確認が必要。ギルドIDはユーザー確認または認証済みの既存設定との厳密照合なしに推測しない。SQLの例・本番登録・実報酬の発行は保留する。
- 承認後には対象ギルド・開始時刻・リリース後Cloudflare D1監視の実施者・停止条件を確認し、追加設定の適用を別途行う。今回のコード配備だけでは発行が始まらない。

Phase 9は実装・CI・Pages/Worker配備完了、報酬は未有効化。**以下は提案であり、ユーザー承認済みではない**。

- **監視担当（PROPOSED）**：ユーザーがCloudflareダッシュボードで本番D1の読取・書込行数、エラーと遅延を確認し、異常を発見したらoversightチャットに報告する。監視周期と代行者は未承認。
