# スパイクラッシュの未支給・遺物差額の補填

2026-11-06、オーナーの指示で一度だけ実行する修復。マージ後のWorker配置が成功すると毎分cronから小分けで進める。追加の秘密設定・手動の本番SQLは不要。

## 対象と計算

- 初回実行時刻を固定し、その時刻までの保存済みスパイクラッシュを対象とする。
- 基礎40／20KPに対して遺物を計算した保存ログから、切り捨て前の倍率・固定効果・鎖・セット・共鳴を復元する。新上限400／200KPまでの額から既支給分を引き、正の差額だけを支給する。
- 遺物が未支給だった試合、旧ログが育成込みだった試合は、当時の `kp_operations.state` の装備を使用する。今の所持・今の装備を過去の試合に使わない。装備変更90分のルールも当時の精算時刻で確認する。
- もともと追加7KPだった試合は、上限を引き上げても計算結果が7KPなら差額0。全試合へ一律400KPを配る処理ではない。
- 速報記録があるのに試合KPがない場合は、Henrikの試合詳細とPUUID・モード・完了・日時を確認。KP開始・本人リンク・スパイク育成開始の全時刻以降だけを対象とする。本文からの成績推定はしない。
- 未支給の基礎報酬には、直前の保存済み育成プロフィールと通常の `quoteSpike` を使う。現在の育成プロフィール・覚醒・連勝記録は巻き戻しも進行もしない。既存の手動補填（`manual-<終了時刻>`）と同じ試合は再支給しない。終了時刻の秒丸めに備え、前後5分の手動補填も重複候補として除外する。

## 整合性と通知

差額記録 `kp_spike_compensation` と台帳・残高は同一SQLiteトリガーで確定。既存の台帳は書き換えない。遺物が全く未支給なら通常の `relic:<event>` キーを使い、通常処理の再試行との二重加算を防ぐ。支給済みの遺物との差額は `spike-comp:<event>` に記録する。残高上限などで失敗すると補填記録もロールバックし、カーソルは進まない。

試合合計・遺物補正・監視処理のキャッシュは両方の台帳行を合算する。元の試合報酬の内訳を維持し、保存済みの速報本文を再構築して通常の編集キューへ戻す。Discordの投稿IDが残っていれば同じ投稿を編集し、削除済みの投稿は従来の配信処理で再投稿する。

全対象の走査後、実入金の合計を**本人ごとに1通**、アカンbotの既存キューへ登録する。

> @本人 **○○ KP給付しました。**
> スパイクラッシュ○試合分の未支給・遺物差額の補填やで。口座へ入金済みや！

対象本人だけを `allowed_mentions.users` に明示。支給0の人には給付通知を出さない。通知の失敗は既存の期限付き配送キューで再試行し、残高を再加算しない。外部送信成功後の通信断などによる通知重複の可能性は既存配送と同じで、完全な一度だけ配送を保証するものではない。

## 保留と実行量

- 当時の装備が残っていない、必要な試合詳細がAPIにない、手動イベントだけで認定済みSpike証跡がない場合は、推定額を入れず理由を保存する。
- そもそもBotにもAPIにも残っていない試合を、この修復だけで発見・証明できるわけではない。試合ID等の根拠が別途必要。
- APIの通信失敗・429はそのカーソルを維持。確定404は未解決として残し、他の試合へ進む。
- 1分につき既存イベント3件、既知の速報10件、追加のHenrik試合詳細取得は最大1回。既存のAPI待機設定も尊重する。
- 完了後は完了フラグのインデックス付き1読取だけで停止し、通常試合を永続的に再集計しない。
- `spike_compensation_ready` ログに対象人数・未解決件数を出す。額・理由は `kp_spike_compensation`、実入金は `kp_ledger`、通知は `mahjong_watch_posts` の `spike-compensation-20261106:notice:` で確認できる。これらの個人別実データは公開PRやログへ転載しない。

保留分の再処理は当時の証跡を確認してから別の修復として行う。完了フラグを消して全員へ同じ額を再配布する必要はない。
