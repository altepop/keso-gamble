## 今回の変更

| 部分 | 修正 | 保持すること |
|---|---|---|
| KP監視の試合照合 | 遺物・補填の同じSUMを二度計算する代わりに、台帳IDの主キーJOINを一度ずつ使う | 金額、補填、保存済み本文、監視回ごとの再確認、別guildの分離 |
| 遺物の個人/全体表示集計 | `kp_relic_totals` に参加者ごとの件数と正負の合計を投影 | 表示用のみ。支給・上限・支出の判定には使わない |
| エージェント使用回数 | 起動時は移行マーカーを主キーで確認し、移行済みなら履歴GROUP BY文を実行しない | 初回移行とその後の原子的な増分・再送重複排除 |
| 通知の今日/ACT集計 | 日付とモード、ACTに結果まで含む索引を追加し、既存の同時刻境界を保持したまま終了時刻の上限を明示 | 同時刻の試合ID境界、連勝、引分、過去試合の集計範囲 |
| 監視成功ログ | DBのUPSERTにも5分間隔を適用し、別isolateの再起動で毎分書き直すことを抑える | 失敗時は即記録。失敗からの回復時は間隔内でもDB更新可能 |
| 日次監視 | 既に取得していたRows writtenを合算して表示、70,000行で警告 | 既存の読取350万警告/400万の任意履歴節約を維持。書込警告で決済を停止しない |

遺物投影は初めて遺物画面を開く際に、一度だけ全台帳から集計する。マーカー・投影・3トリガーを同じD1 batchで導入し、二つの初回起動が競合しても加算を重ねない。以後は台帳挿入と同じトランザクションで該当参加者の一行を更新する。更新/削除による管理修正にも追随する。通常の台帳登録はINSERT/INSERT OR IGNOREであり、REPLACE運用はしない。

読み取りを投影へ置き換えるため、遺物台帳の変更に投影一行ぶんの書込が増える。追加索引も初回作成と索引列の変更に書込が必要。このためRows readだけで成功とは判定しない。新しい定期ジョブやポーリングは追加しない。

## 検証

- 実SQLiteで1万件の遺物台帳を投入し、5人分の投影5行から同じ合計を取得。個人は主キー、全体はguild索引検索となり、画面の集計で台帳を読まないことをEXPLAINで確認。
- 初回競合・初回失敗のロールバック・再試行・同じ台帳の再送・正負/ゼロ額・所有者/guild移動・種別変更・削除・未コミット更新を検証。台帳自体の保持も確認。
- 旧エージェント実装で再起動時の履歴走査を再現するテストが失敗し、修正後は成功。
- 通知4,002件の修正前後で日次/ACT結果を比較し、同時刻の境界と引分を維持。新索引のカバリング検索とソート不要を確認。
- 監視の別DB bindingで、同じ成功ログの更新が間隔内に発生しないこと、失敗・回復は記録されることを確認。
- 全サービスcheck、Activity、Worker build、Chromium/WebKit CIの最終結果・本番バージョンは今回のPRに記録する。

これらはローカルの正しさとSQL計画の検証であり、Cloudflare課金行数の削減率を実測したものではない。

## 本番での完了判定

1. main CIとWorker配置を確認する。Pages成功だけでWorker反映済みとはしない。
2. 既存の毎時監視で、初回移行後の1h/24hとアカウント全体UTC-dayのread/writtenを記録する。
3. 通常利用とピークを含む複数日、可能なら7日を比較。Free目標はread100万〜150万/日、write10万/日未満に十分な余裕を持つこと。両DBのアカウント合算で判断。
4. 直後の24h窓には修正前の処理と初回移行が混在する。低利用やquota拒否による見かけの低下を成功と誤認しない。

将来の負荷増に対する「完全に無料枠を超えない保証」や、実測前の大幅削減率は約束しない。元の追跡Issueは [#207](https://github.com/altepop/keso-gamble/issues/207)。

## 戻す場合

Workerコードを直前版へ戻しても投影は残す。遺物表示の旧集計は台帳から読めるため、資産を巻き戻す必要はない。投影の再構築が必要なら、管理下でマーカー `relic_economy_v1` を除去して次回の原子的な再集計を行う。この変更はその削除を自動実行しない。新索引は金銭データではなく、必要に応じた除去を別に判断する。
