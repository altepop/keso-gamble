# 参加者拡大・他ゲーム報酬・指令の拡張案

2026-10-27。現行コードを確認した設計案。実装済み・自動支給中とは扱わない。

## ユーザーの要望

登録済み4人以外にもKPを獲得する遊び方を用意する。麻雀の段位戦、Steam実績、Minecraftの採掘量、VCT QUIZとKESO LOOPの実績を対象にする。Steamの取得率0.1%の実績は5,000 KP。VALORANT以外の指令も種類を用意する。

「0.1%以下」まで同額にすること、その他の報酬・価格・制限は以下の提案。まだ有効化しない。

## 実コードの確認結果

- 現行Activity認証は `services/valorant-results/src/discord-activity-auth.ts` の登録4人の対応表で拒否判定。KP API・セッション発行・相手一覧も同じ対応表を使用。認証の一行だけ緩めても未登録者は遊べない。
- VALORANTのRiot/Discord対応表と、一般参加者の口座を分離する必要がある。既存4人の残高・台帳・セッションを維持する。誰でも登録する方式と対象Discordサーバーメンバー限定方式は未確定。サーバー限定ならDiscordの所属をサーバー側で確認し、ブラウザーのguild_idは根拠にしない。
- VCT QUIZの `server/src/solo/AchievementStore.ts` はDBトランザクション内で `player_achievements` を一意に登録し、新規実績IDを返している。`shared/src/achievements.ts` に完走・全問正解・日課・ランク勝利・最高段位・LOCK INなどの記録がある。
- KESO LOOPの `packages/game-data/src/progress.ts` に `first_clear`、`clear_10`、`chapter2`、ボス・挑戦・熟練などの実績定義がある。セーブ値の判定だけではKP支給の証拠にしない。本番側の本人確認とサーバーによる進捗確定経路は別途確認が必要。
- 上記アプリと現在のKP口座の間に、今回確認した範囲で支給接続はない。本番の有効なVALORANT報酬は変更しない。

## 獲得側の案

| 遊び | 支給条件 | KP案 | 確認方法・未接続部分 |
| --- | --- | ---: | --- |
| 麻雀 | 段位戦の完走 / 1位 | 50 / 追加100 | サービス名を確認後、公式に取得可能な牌譜・対局IDで本人と順位を照合。友人戦と退出は別扱い |
| 麻雀 | 新しい最高段位 | 段位ごとの初回報酬 | 降段→再昇段では再支給しない。四麻・三麻やサービスごとの体系を識別 |
| Steam | 取得率0.1%の承認対象実績を本人が解除 | **5,000** | Steam本人リンク＋本人の解除状況＋公式全体取得率をサーバー側で取得。対象ゲームと実績を登録 |
| Steam | その他の対象実績 | 100〜3,000 | 難易度と取得率で台帳化。取得率だけを難易度とみなさない |
| Minecraft | 対象ブロックの採掘1,000個ごと | 20 | 管理するサーバーの記録でUUID照合。対象版・サーバー未確認 |
| VCT QUIZ | 日課 / ランク勝利 / 新規実績 | 30 / 100 / 100〜3,000 | サーバー確定イベントから支給。日課の同日再挑戦・既知問題の周回は重複支給しない |
| KESO LOOP | 初周回・初章到達・初ボス・初挑戦達成 | 100〜3,000 | 実績ID単位で一度。クライアントの自己申告進捗では支給しない |

麻雀・クイズの繰り返し報酬と採掘報酬には別々の日次上限を置く案。既存のコンペ報酬へ後付けで制限しない。初期は新しい獲得経路を一つずつ有効にし、獲得量を見て調整する。

Steamは対象を無制限にすると、低取得率でも簡単な実績・実績専用ゲーム・外部解除ツール等で経済が変わる。APIで解除履歴を確認できてもプレイ過程の公正性までは証明できない。5,000 KP対象は承認した実績に絞り、取得率の数値・取得日時・規則版を保存する。API実値で判断し、画面の丸め表示は使用しない。API未公開・非公開プロフィール・欠損時は保留。解除済み実績の過去分支給は別途決定する。後日取得率が変わっても、同じ本人の同じ実績へ再支給しない。

Minecraftは設置→破壊の反復や自動収穫で無限にKPを作らないよう、対象ブロックを限定する。Javaの統計を読むだけでは設置ブロックや採掘場所を区別できない。必要な場合はサーバー側プラグイン等で記録する。累積カウンターの減少・リセット・ワールド作り直しで初期分を再支給しない。初回接続時の値を基準に差分だけ集計する案。

## 使い道の案

相手が参加できるゲーム・受けられる指令を登録し、それに合う商品を表示する。VALORANT未登録者にも共通商品を用意する。既存の通常コンペ2,500、ソロコンペ15,000、ソロデスアンレ20,000 KPを維持する。

| 種類 | 商品例 | 価格案 | 達成条件 |
| --- | --- | ---: | --- |
| 麻雀 | 段位戦1戦 | 1,500 | 購入後の対象段位戦を完走 |
| クイズ | 指定範囲・難易度で1回挑戦 | 800 | サーバーがその設定で完走を確認 |
| クイズ | 対戦部屋へ1戦参加 | 1,000 | 指定部屋の対戦完了。勝利は要求しない |
| KESO LOOP | 指定の挑戦を1周 | 1,500 | 指定challenge IDで完走 |
| Steam | 指定ゲームを30分プレイ | 2,000 | 通常のSteam総プレイ時間だけで正確な30分を保証できるか確認するまで販売保留 |
| Steam | 指定の未解除実績を解除 | 3,000〜10,000 | 購入時に未解除・購入後の解除を確認。既存の5,000 KP獲得報酬との併給ルールも明記 |
| Minecraft | 対象素材の採掘依頼 | 1,000〜3,000 | 発令時以降の対象ブロック数 |
| Minecraft | 指定素材の納品 | 1,000〜3,000 | サーバー側で納品を確定。採掘と所持と納品は別条件 |
| 共通 | 一緒に遊ぶ1戦券 | 1,000 | 対象ゲームを決めて一緒の試合を完走。共通の参加記録が取れない場合は手動確認と明記 |

自由記述は補足にとどめ、機械判定する条件には商品ID・ゲームID・実績ID・ブロックID・数量などを持つ。達成不能な実績、既に解除済みの実績、相手が持たないゲームを自動で購入可能にしない。期限、相手の進行中件数、取消・返金、購入後の達成、失敗と途中退出の扱いを商品単位で決める。自動確認できる商品と手動確認の商品を明示する。

## 共通の実装方式

1. 参加者テーブルとVALORANTリンクテーブルを分ける。Discord本人認証を入口に口座を作る。SteamID・Minecraft UUID・麻雀の本人IDは別々に所有確認して紐付ける。名前の一致で紐付けない。
2. 確認元が `source, sourceUserId, achievementId/matchId/counterId, occurredAt, evidence` を確定する。送信元が支給額を好きに指定するAPIにはしない。KP側のルール表で金額を計算する。
3. VCT QUIZ等は実績登録と同じDBトランザクションで送信待ちイベントを保存する。別サービスへのHTTP送信はコミット後。送信失敗で実績も報酬も失わない。
4. サービス別の認証鍵・本文署名・時刻と送信先を検証する。Activityや一般ブラウザーからの実績申告を信頼しない。秘密鍵をフロントへ置かない。
5. 外部実績の一意キーは `guild + source + sourceUserId + achievementId`、対局はmatchId、採掘は正規カウンター区間。設定版・受信時刻・名前変更でキーを変えない。本人リンクの付け替えで同じ外部実績を別口座へ再支給しない。
6. 支給・台帳・残高は原子的に確定し、重複イベントには元の結果を返す。支給イベントを入れるだけで指令達成も二度処理しない。
7. 未接続の項目は一覧に「準備中」と表示できるが、実際に支給された・自動判定できると表示しない。未確定額を0 KPの支給済みとして消費しない。

## 実装順

A. 新規参加者の口座・相手の参加ゲーム設定と共通指令カタログ。
B. VCT QUIZのサーバー実績イベント→KP台帳（実績・日課・ランクの順）。
C. Steam本人連携・承認対象実績・0.1%/5,000 KP。
D. KESO LOOPの本人・サーバー確定進捗の確認後に連携。
E. 麻雀サービスとMinecraft運用環境の回答に合わせて接続。

未決定: 一般参加範囲、Steamの対象ゲーム、その他の金額・支給開始日時・過去分支給・指令の取消と期限。


## 確定した利用環境（ユーザー回答）

麻雀は **雀魂**。Minecraftは **Java版Realms**。別サーバーへの移転は承認も提案採用もされていない。

### 雀魂

段位戦の牌譜URL・対局IDを確認する方式から検討する。段位戦/友人戦、四麻/三麻、対局者本人、完走と順位の検証が必要。非公式の通信解析用APIや第三者収集サービスを、公式の安定した履歴APIとして扱わない。公式に利用可能な取得経路が確認できなければ、牌譜URLを添えた申請と管理者確認で始め、自動支給中とは表示しない。雀魂のログインパスワードを集めない。

### Java版Realms

Realmsでは一般的なPaper/Spigotサーバープラグインを導入する方式は使わない。候補は以下。

- ダウンロードしたワールドの `stats/<uuid>.json` などの統計を、管理者が取り込む。プレイヤーが編集したJSONをそのまま本人の証拠として提出する仕組みにしない。手動の世界取得が必要で、常時の自動支給ではない。
- 管理者がデータパックをワールドへ導入して採掘を記録する案。データパック単体で外部KP APIへHTTP送信できるとは扱わない。外部へ記録を取り出す経路が別に必要。ワールド操作は仕様確定後。

まずは対象ブロック・累積値の基準・UUIDの本人対応・管理者取込・既支給との差分を記録する設計にする。統計だけでは設置→破壊、自然生成ブロック、採掘場所などを十分区別できないので、対策未実装なら低額・上限付きか保留と明記する。Realmsの採掘自動支給を、VCT QUIZ等の接続の前提にはしない。
